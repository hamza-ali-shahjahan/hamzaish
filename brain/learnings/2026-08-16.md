# Learnings — 2026-08-16

## The legibility gate lints the sentence, never the claim
`check-legibility` has been enforcing receipts since 2026-08-01 — vocabulary,
shape, word caps, one next command. What it cannot do is notice that
"Checked: gates pass" is false. The receipt's most load-bearing line was the one
line with no verification behind it, and nobody caught it because the gate that
looked at it *was passing*. A gate green on the wrong axis is worse than no gate:
it buys confidence at exactly the point where confidence should be earned.

Fix shipped: `bun run verify` spawns each gate, records the true exit code to a
hash-chained ledger, and renders the Checked line from records. Empty ledger →
"nothing was verified." The first real run proved the point immediately —
`check-counts` failed on a rule-#12 violation (`products/valuable` carrying an
absolute machine path in a permanently-public repo) that had been sitting
unnoticed, plus five README counts that went stale the instant a skill was added.
**A hand-written receipt would have said "gates pass" and been believed.**

**Meta-lesson: when adding a gate, ask what class of failure it is blind to BY
CONSTRUCTION — and build the second instrument for that class.** Studied version:
`deepseek-harness` ships `lint_printf`-style source linters precisely because its
host-native tests link real libc and therefore cannot see formatter bugs. Knowing
what your fast loop structurally cannot catch is the sophisticated half.

## Naming the ceiling honestly is cheaper than earning the stronger claim
The obvious framing for the ledger was "unforgeable," borrowed from fable-os,
whose kernel genuinely cannot let a model forge a trace line. We have no ring-0
boundary — a session with a shell can append a false record. Calling it
unforgeable would have been the exact failure the mechanism exists to prevent, in
the mechanism's own announcement.

Shipped as **tamper-evident, not unforgeable**, said in the code, the README, the
evidence folder, and the decision record. Cost: one adjective. Benefit: the claim
survives someone reading the source.

## Ratchets beat walls, and the precedent was already here
`check-limitations` would have failed 73 of 74 skills on day one; `check-decisions`
28 of 30 records. Both shipped as ratchets with grandfathered backlogs — not a new
idea, just the 2026-07-02 eval-coverage precedent applied again rather than
re-litigated. **Reusing a decision is a feature; the decision log exists so the
second instance is cheap.**

The measurement was the payoff: **26 of 28 decision records are missing only
`alternatives`.** Decision, why, wrong-if and revisit were all being done well.
The factory records what it chose and never what it beat — which is precisely the
re-litigation trap the `deepseek-harness` note format calls out. A gate found a
specific, fixable pattern that reading 30 files by hand would not have.

## Both studied repos measure their machinery and neither measures their agent
`fable-os`: 9.6M assertions, zero repeated trials, says so plainly. `deepseek-
harness`: 961 test files, 1.29:1 test-to-source, a 100%-per-file coverage merge
gate — and a 3-line `BENCHMARK.md` that delegates benchmarking to an external
caller. Searches for swe-bench / rubric / as-a-judge return one doc comment.

Two serious, well-resourced projects both prove correctness exhaustively and
capability not at all. **That is the white space the eval layer here already
stands in — at 13% coverage, which is thin against our ambitions and ahead of the
field.** The strategic error would be chasing their architecture instead of
deepening the thing neither of them has.

## The gate caught its own author, twice
Adding one skill turned `check-evals` red (new skill, no eval case) and moved
five README counts stale. Both were mine, both surfaced within seconds, neither
would have been noticed by a session reviewing its own work. A ratchet that only
constrains future contributors is decoration; one that fails the person who wrote
it is doing its job.
